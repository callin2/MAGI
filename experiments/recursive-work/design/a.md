## 독립 분해 평가 A

### 1. 가장 작고 유용한 사용자 산출물

가장 작은 유용한 결과는 사용자가 자연어로 제시한 하나의 운영 목표를 실제 검토 가능한 “완결 업무 패키지”로 바꾸는 파일럿이다. 예를 들어 사용자가 “온실에서 토양 수분이 낮으면 펌프를 켜고, 위험 조건이면 중지하는 자동화 절차를 설계해 달라”고 입력하면, 최종 산출물은 단순한 역할 분담 기록이나 기억 실험 결과가 아니라 다음을 포함해야 한다.

- 목표와 성공 조건을 명시한 요구사항 요약
- 실행 가능한 자동화 절차 또는 코드 수준의 구체 산출물
- 책임·입출력·의존성·검증 결과를 연결한 추적표
- 실패한 판단, 재시도 또는 재분해 기록
- 사용자가 결과를 검토하고 다음 행동을 결정할 수 있는 짧은 설명

현재 저장소의 `role_memory.py`는 이 과정의 상태·binding·후보·검증·철회·scope/grant·revision 영수증을 기록하는 기반으로 재사용한다. 다만 기억이 저장됐다는 사실 자체를 제품 가치로 삼지 말고, 하나의 실제 업무 결과가 완성됐는지를 최종 기준으로 둔다.

### 2. 경쟁 분해안과 선택

경쟁안 A는 기능 중심 분해다. `role_memory.py` 개선, 입력 CLI, 결과 문서 생성, 테스트 추가를 각각 leaf로 나누고 마지막에 연결한다. 구현은 빠르지만 사용자 목표에서 출발하지 않기 때문에 기존 문제처럼 코드·이슈·보고서만 늘어나고 실제 산출물이 비어 있을 위험이 크다.

경쟁안 B는 사용자 결과 중심의 수직 슬라이스다.

1. 하나의 구체 목표와 완료 조건을 고정한다.
2. 목표를 요구사항·실행안·검증안으로 분해한다.
3. 각 결과를 독립적으로 생성하고 역할 기억에 기록한다.
4. 조정자가 충돌을 해결해 실행 가능한 패키지로 통합한다.
5. 실제 결과와 실패 경험을 함께 평가한다.

이 안을 선택한다. 현재 가장 큰 미해결점은 저장소 기능 부족보다 “협업이 실제 사용 가능한 결과를 만들었는가”이므로, 저장소 변경을 최소화하면서 목표부터 결과까지 한 번 관통해야 한다. 경쟁안 C인 다수 에이전트의 병렬 자유 탐색은 다양한 의견을 얻을 수 있으나, 이번 파일럿에서는 통합 비용과 책임 불명확성이 크다. 독립 판단은 안전·완료 기준·충돌처럼 결정이 필요한 지점에만 사용하고, 명확한 작성·실행은 바로 수행한다.

### 3. 실행할 leaf

#### Leaf 1: 목표·완료 계약 작성

- 책임: 요구사항 분석 역할
- 입력: 사용자의 자연어 목표, 관련 기존 문서와 현재 저장소의 제공 기능
- 출력: 목표, 범위, 성공 조건, 제외 범위, 필요한 입력·출력, 위험 조건
- 의존성: 없음
- 완료 검사: 사용자가 결과를 검토할 수 있는 구체 산출물이 정의되고, “코드 작성”이 아닌 업무 결과가 성공 조건에 포함되어야 한다. 모호하거나 서로 충돌하는 조건은 후보로 표시하고 독립 검토 대상으로 넘긴다.

#### Leaf 2: 실행 산출물 생성

- 책임: 실행 설계·구현 역할
- 입력: Leaf 1의 확정 계약, 기존 코드와 문서
- 출력: 재사용 가능한 실행 절차, 필요한 최소 코드 또는 설정, 결과 예시
- 의존성: Leaf 1 확정
- 완료 검사: 표준 라이브러리와 기존 기반으로 재현 가능하고, 사용자가 실제 결과를 열어 검토할 수 있어야 한다. 외부 모델 API나 대형 프레임워크를 전제하지 않는다. 실행이 불가능한 부분은 가정과 대체 증거를 명시한다.

#### Leaf 3: 독립 검증·통합 입력

- 책임: 검증 역할
- 입력: Leaf 1 계약과 Leaf 2 산출물
- 출력: 성공·실패 판정, 계약 위반 목록, 사용자용 통합 요약, 다음 개선 후보
- 의존성: Leaf 2 결과
- 완료 검사: 정상 경로뿐 아니라 잘못된 입력, 권한/scope 충돌, 검증 실패·철회, 재실행 시 revision 일관성을 확인한다. 통합 조정자는 원문 판단과 조정 결과를 구분해 기록한다.

### 4. 통합·실패·재분해·중단 기준

통합 순서는 계약 확정 → 실행 산출물 확인 → 독립 검증 → 조정자 통합이다. 각 leaf는 입력 버전과 revision을 함께 남겨, 어느 판단이 어떤 상태에서 생성됐는지 추적한다. 통합 시 의견이 다르면 다수결로 숨기지 않고 충돌 지점, 근거, 선택 이유를 기록한다.

재분해는 다음 경우에만 한다. 목표가 두 개 이상의 독립 사용자 결과로 갈라졌거나, 하나의 leaf가 서로 다른 책임·입출력·검증을 동시에 갖거나, 실패 원인이 실행과 검증 중 어디에 있는지 분리되지 않을 때다. 재분해는 기존 결과를 폐기하지 않고 실패한 leaf와 새 leaf의 관계를 revision으로 남긴다.

중단 기준은 위험한 동작을 검증 없이 실행해야 하는 경우, 핵심 입력이나 권한이 없어 결과를 재현할 수 없는 경우, 통합 후에도 성공 조건을 판정할 증거가 없는 경우다. 이때는 추측으로 완료 처리하지 않고, 사용자에게 필요한 추가 입력과 현재까지의 검증 가능한 산출물을 제출한다.

### 5. 경험과 다음 과제로의 전이

이번 파일럿의 경험은 단순히 성공/실패로 저장하지 않는다. 목표 유형, 분해안, 선택 이유, 각 leaf의 실제 입력·출력, 반복 교정 횟수, 토큰 또는 작업량 변화, 실패 원인, 재분해 여부, 최종 사용자 판정까지를 짧은 실행 기록으로 남긴다. `role_memory.py`에는 역할별 state와 binding, 후보·검증·철회, scope/grant, revision 영수증을 사용하되, 기억 항목마다 실제 결과와 연결된 증거 위치를 붙인다.

다음 과제로 전이할 때는 “이 역할이 유용했다” 같은 일반 문장보다 조건부 규칙을 만든다. 예를 들면 “목표가 장치 제어를 포함하면 실행 leaf가 추상 절차만 제출하지 않고 입력·출력·안전 중지 조건을 포함해야 한다”, “검증 증거가 문서 수준이면 물리 실행 완료로 승격하지 않는다”처럼 재사용 가능한 판단 규칙으로 기록한다. 다음 파일럿은 이번 규칙을 적용해 같은 목표를 더 적은 사용자 교정으로 완성하는지를 비교한다.
