# 독립 평가 B

## 1. 가장 작고 유용한 사용자 산출물

가장 작고 유용한 사용자 산출물은 “한 번의 실제 업무를 끝까지 완료한 검토 패키지”다. 사용자가 자연어 목표 하나를 주면, 그 목표를 책임별로 나누고 필요한 판단을 수행한 뒤 결과물을 만들고, 검증 근거·실패·미완료 항목까지 묶어 보여준다. 저장소 기능을 시연하는 보고서나 합성 기억 예제가 아니라, 예를 들어 “특정 사용자를 위한 자동화 제안서와 실행 가능한 설정 파일을 만들고 검증 결과를 첨부”하는 식의 목적→완성 산출물이어야 한다. 범위는 텍스트·구조화 파일·검증 로그 정도로 제한해 실제 사용자 검토가 가능하고 재현 가능한 한 건을 완결한다.

## 2. 경쟁안과 선택

안 A는 순차 파이프라인이다. 목표 해석 → 산출물 작성 → 검증 → 통합을 고정 순서로 실행한다. 구현과 실패 추적은 쉽지만, 초기에 잘못 해석한 목표가 뒤 단계까지 전파되고 독립적인 판단 비교가 없다. 현재 저장소의 CLI와 SQLite 계약을 가장 적게 건드릴 수 있다는 장점은 있다.

안 B는 책임 분리형 소규모 DAG다. 목표와 완료 조건을 먼저 구조화하고, 서로 독립인 두 판단 leaf가 해석·접근법을 제시하며, 실행 leaf가 하나의 선택된 안을 산출물로 구현하고, 검증 leaf가 결과와 계약을 독립 점검한다. 조정자가 근거를 비교해 선택하고 통합한다. 이 안을 선택한다. 현재 문제는 기능 부족보다 “보고서와 이슈만 늘고 실제 결과가 없다”는 실행·통합 실패이므로, 독립 판단을 모든 작업에 강제하지 않으면서도 중요한 해석 충돌과 완료 판정을 분리할 수 있기 때문이다. 단순하고 이미 명확한 파일 생성은 바로 실행하며, 경쟁 판단은 목표 경계나 산출물 형태가 불명확할 때만 사용한다.

## 3. 실행 leaf

- 목표·완료 계약 leaf: 사용자 목표를 사용자 가치, 입력, 제약, 최종 산출물, 완료 검사로 구조화한다. 입력은 원문 목표와 기존 계약, 출력은 작업 계약과 예상 산출물 스키마다. 목표가 관찰 가능한 결과로 표현되고 코드 작성이 완료 조건으로 남지 않는지 검사한다.
- 산출물 실행 leaf: 계약에 따라 실제 사용자 결과를 만든다. 입력은 계약과 필요한 role/state/binding 및 후보·grant 범위, 출력은 최종 파일 또는 문서, 실행 명령·결과 요약·revision 영수증이다. 결과가 소비 가능한 형식이고 빈 계획서가 아닌지 검사한다.
- 검증·반증 leaf: 계약과 산출물에 대해 독립적으로 사용·검토하고 실패를 재현한다. 입력은 계약, 산출물, 로그와 revision 증거, 출력은 통과/실패, 결함, 재현 절차, 수정 후 결과다. 핵심 기준을 실제 명령으로 재실행하고 성공 주장과 증거가 일치하는지 검사한다.

## 4. 통합·실패·재분해·중단

조정자는 원문 목표, 선택한 분해, 각 결과와 조정 이유를 통합한다. 계약과 산출물이 불일치하면 해당 leaf를 재실행한다. 실행 오류나 누락 입력 같은 국소 실패는 해당 leaf만 재시도한다. 목표 해석 충돌, 완료 기준의 모순, 두 번의 수정에도 같은 실패가 반복되면 실패를 해석/실행/검증/외부 의존성으로 분류해 경계만 재분해한다. 필수 입력·권한·외부 시스템이 없고 안전한 대체가 불가능하거나, 검증 가능한 사용자 산출물을 만들 수 없거나, 재시도 비용이 결과 가치보다 크면 중단하고 부분 결과와 차단 근거를 남긴다.

## 5. 경험 전이

매 실행마다 목표 계약, 선택한 분해, leaf별 입출력, 실패 원인, 검증 증거, 사용자 수정을 구조화해 저장한다. role_memory의 state/binding과 revision 영수증으로 판단 출처와 변경 이력을 보존한다. 다음 작업에서는 실제로 수정된 해석, 재사용된 분해, 반복 실패 패턴만 검색한다. 전이는 토큰 저장이 아니라 유사 목표에서 설명·교정 횟수 감소, 첫 산출물의 계약 충족률 증가, 검증 실패의 조기 발견으로 측정한다. 측정되지 않으면 기억 기능을 확장하지 말고 실제 사용자 업무를 더 수행해 전후 증거를 만든다.
