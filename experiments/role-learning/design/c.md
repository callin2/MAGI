## MAGI #13~#15 독립 설계 평가

세 계약은 하나의 저장 구조를 정하는 일이 아니라, “누가 어떤 상태를 어떤 조건으로 읽고, 어떤 교훈을 어느 범위에 적용했는가”를 재현하는 최소 판정 체계로 정의해야 한다. 파일 저장·git 버전·새 세션에서의 파일 읽기는 기반으로 재사용할 수 있지만, 그것만으로 승계·학습·효과를 인정하지 않는다. 세 계약의 공통 식별자는 `roleId`, `agentId`, `workId`, `sessionId`, `stateId`, `revision`이다. 모든 적용 기록에는 사용한 상태 revision과 교훈 ID, 판정 결과를 남긴다.

### #13 역할·지속 상태 계약

계약의 핵심은 역할과 상태를 분리하는 것이다. `roleId`는 책임·목적·판단 기준의 버전 있는 정의이고, `agentId`는 실행 주체의 정체성이다. `workId`는 한 작업, `sessionId`는 한 대화·프로세스 실행, `stateId`는 작업이 끝나도 남는 지속 상태다. `roleId`만 같아서는 승계가 성립하지 않으며, 실행 시 명시된 `stateId@revision`을 읽고 그 사실을 적용 로그에 기록해야 한다. 상태는 역할 범위, 유효 기간, 상위 프로젝트 범위를 가진다.

역할 변경은 새 `roleRevision`을 발급한다. 책임이 추가되면 기존 상태를 그대로 승계하지 않고 호환성 판정을 거친다. 겸임은 한 agent가 여러 role binding을 갖되 역할별 상태와 검색 범위를 분리한다. 해제된 역할은 새 작업에 바인딩할 수 없고, 기존 상태는 보존하되 읽기 권한을 철회한다. 동일 역할의 새 agent는 동일 역할용으로 명시된 `stateId`만 승계할 수 있으며, 전용 agent 상태는 자동 승계하지 않는다. 프로세스·세션 재시작은 `stateId@revision` 재연결과 무결성 확인이 모두 성공해야 복구로 판정한다.

대안은 두 가지다. 첫째, 역할 중심 단일 상태다. 구현이 단순하고 같은 역할의 전이가 쉽지만, 겸임과 전용 경험이 섞일 위험이 크다. 둘째, agent 중심 상태에 역할별 읽기 인덱스를 두는 방식이다. 귀속이 명확하지만 새 agent 승계와 공유가 복잡하다. 최소 구현은 역할 중심 상태를 기본으로 하되, 상태 내부에 `ownerScope`와 역할 revision을 필수로 넣는 절충안이 적절하다.

가장 강한 반례는 “같은 역할명과 같은 파일이 있으므로 승계됐다”고 보고했지만 실제 실행은 다른 프로젝트의 상태를 읽은 경우다. 수용 조건은 새 세션에서 지정된 `stateId@revision`을 읽었다는 증거, 적용된 교훈 ID, 역할·프로젝트 범위 일치, 범위 불일치 시 거부 기록이다. 최소 실행 경로는 역할·agent·state manifest와 재연결 로그를 기존 파일/git 기반으로 구현하는 것이다. 후속 이슈는 역할 revision 변경, 겸임 격리, 재시작 복구 실패, 상태 삭제·철회 경계를 다룬다.

### #14 교훈 수명주기 계약

교훈은 `event`, `observation`, `hypothesis`, `lessonCandidate`, `validatedLesson`을 구별한다. 후보에는 원인 가설, 적용 조건, 근거 event ID, 검증 상태, 생성 revision을 포함한다. 후보는 자동 생성할 수 있지만, 기술적 판단은 합의된 목적·제약·시험 방법이 있으면 agent가 검증한다. 새로운 취향, 사업 가치, 권한, 위험 허용 수준을 바꾸는 선택은 인간 판단으로 남긴다.

상태 전이는 `candidate → validated | held | rejected`이며, 검증된 교훈도 `active → superseded | revoked`가 될 수 있다. 단일 성공, 칭찬, 불만은 후보 근거일 수 있으나 단독으로 validated가 될 수 없다. 반복 재현, 반례 점검, 적용 범위 확인이 최소 검증 조건이다. 철회는 새 revision으로 기록하고 이전 revision을 삭제하지 않는다. 검색기는 active이고 범위가 맞는 최신 revision만 반환하며, 철회된 교훈이 캐시나 기존 세션에 남아 있으면 적용 전에 무효화해야 한다.

대안은 전면 인간 승인 방식과 자동 검증 승격 방식이다. 전자는 가치 오판을 줄이지만 모든 교훈이 병목이 된다. 후자는 속도는 높지만 단일 성공을 일반 규칙으로 만들 위험이 있다. 최소안은 “기술 판단은 자동 검증 가능, 가치·권한·위험 선택은 인간 승인”이라는 경계와, 후보·검증·철회 이력의 불변 보존을 결합하는 것이다.

가장 강한 반례는 특정 입력에서 한 번 성공한 뒤 “항상 이 절차를 사용하라”는 교훈으로 확정되어 다른 맥락에서 실패하는 경우다. 수용 조건은 단일 성공만으로 승격되지 않음, 적용 조건 밖 검색 시 보류·거부, 철회 후 새 실행에서 검색되지 않음, 수정 revision이 적용 로그에 나타남이다. 최소 실행 경로는 후보 JSON 계약, 수동 또는 단순 규칙 기반 검증 판정, active/revoked 검색 필터, 원인 event 연결이다. 후속 이슈는 검증 샘플 수, 반례 정책, 자동 후보 중복 병합, 캐시 무효화, 교훈 폐기 보존 기간이다.

### #15 지식 귀속·공유 계약

지식은 `private(agent)`, `role-scoped`, `project-scoped`, `explicit-shared` 범위 중 하나를 명시한다. 기본 공유 범위는 보수적으로 `private` 또는 동일 역할의 지정 상태로 두고, 공유는 명시적 대상 role/project와 revision을 가진 승인된 링크로만 허용한다. 동일 역할의 다른 agent는 role-scoped 지식을 읽을 수 있지만, 자동으로 private 상태를 읽을 수 없다. 다른 역할로 공유할 때는 원래 교훈의 적용 조건을 유지하고, 새 역할의 검증 결과를 별도 교훈으로 기록한다.

읽기와 쓰기 권한은 분리한다. 수신 역할은 공유 지식을 읽고 적용할 수 있지만 원본을 수정하지 못하며, 수정은 새 revision 또는 파생 교훈으로 남긴다. 공유 철회는 source revision을 revoked로 만들고 대상 역할의 검색 인덱스와 캐시에서 제거한다. 충돌은 범위가 좁고 최신이며 명시적 대상인 규칙을 우선하되, 가치·권한·안전 제약 충돌은 적용을 중단하고 인간 판단을 요청한다. 역할 변경이나 프로젝트 이탈 시 공유 링크는 재검증하며, 자동 확장은 금지한다.

대안은 전면 비공유와 공용 지식 풀이다. 전면 비공유는 오염을 줄이나 전이 효과를 검증하기 어렵다. 공용 풀은 검색이 쉽지만 다른 역할의 맥락과 위험한 규칙이 섞인다. 최소안은 private 기본값, 동일 역할 범위의 선택적 공유, 다른 역할은 명시적 공유만 허용하는 3단계 모델이다.

가장 강한 반례는 역할 A의 장비·권한 전용 교훈이 역할 B에 전달되어, B가 조건을 충족하지 않은 상태에서 그대로 실행하는 경우다. 수용 조건은 private 비노출, 지정 공유만 노출, 프로젝트 변경 뒤 오적용 거부, 철회 후 재사용 방지, 충돌 시 적용 중단이다. 최소 실행 경로는 각 지식 항목의 `ownerScope`, `readers`, `writePolicy`, `sourceRevision`, `revocation` 필드를 추가하고 검색 시 범위 필터를 강제하는 것이다. 후속 이슈는 공유 승인 표현, 역할 해제 시 재검증, 충돌 우선순위, 캐시 제거와 감사 로그다.

### #16 최소 시험 경로와 판정

#16에서는 R과 S 두 역할, 경험 작업과 별도 전이 작업, 새 세션·프로세스 재시작을 고정한다. 세 조건을 같은 모델·도구·예산으로 비교한다.

- 기억 없음: 상태와 교훈을 제공하지 않는다.
- 원문 로그 검색: 과거 로그는 검색하지만 정제 교훈은 제공하지 않는다.
- 정제 교훈 검색: 검증된 교훈만 제공한다.

성공은 별도 전이 작업에서 사전 복사·재설명 없이 올바른 `stateId@revision`과 교훈을 조회하고, 역할 범위에 맞게 적용하며, 정답·오류·철회 조건을 기록하는 것이다. 실패는 같은 역할명만으로 승계를 통과시키거나, private 지식이 노출되거나, revoked 교훈을 재사용하거나, 기술적 근거 없이 새 가치 결정을 자동 확정하는 것이다. 저장·검색·입력 포함·실제 적용·성과를 각각 증명해야 한다.

반복 횟수, 성공률, 오류·재설명, 잘못된 확신, 생성·검토·검색·조정 호출과 총 시간·토큰을 측정한다. 이득이 없거나 총비용이 증가해도 유효한 결과로 기록한다. 세 계약의 최소 구현과 실제 시험은 각각 선행 이슈로 등록한 뒤 진행하며, 파일 존재·합의·저장 성공은 #16의 효과 입증으로 간주하지 않는다.
