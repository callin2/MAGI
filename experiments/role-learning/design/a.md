## 독립 설계 평가 A — MAGI #13~#15

세 이슈는 하나의 “기억 파일” 계약으로 합치기보다, `정체성·지속 상태`, `교훈 수명주기`, `귀속·공유 범위`를 서로 참조하는 세 계약으로 유지해야 한다. 저장 성공이나 파일 조회만으로 승계를 인정하지 않고, 새 실행이 특정 revision을 읽고 실제 판단에 사용했는지까지 추적해야 한다. #10에서 재사용할 수 있는 것은 git/파일 기반 지속, JSON 자료 계약, 새 실행의 관련 지식 조회, 변경 이력 보존이다. 별도 구현이 필요한 부분은 귀속 경계, 후보 상태 전이, 철회 전파, 충돌 판정, 실제 전이 증거다.

### #13 역할·정체성·지속 상태 계약

핵심 식별자는 다음처럼 분리한다.

- `roleId`: 추상적 책임과 판단 기준을 식별한다. 표시 이름은 별도이며 이름만으로 동일성을 판정하지 않는다.
- `roleVersion`: 책임·판단 기준의 변경 버전이다.
- `agentId`: 특정 에이전트 주체의 안정적 식별자다. 모델이나 프로세스 ID와 동일하지 않다.
- `assignmentId`: agent가 특정 role을 수행하는 위임 관계다. 겸임이면 여러 assignment가 존재한다.
- `workId`: 작업의 식별자다.
- `sessionId`와 `runId`: 대화 세션과 실제 실행을 구분한다.
- `stateId/stateRevision`: 재연결할 지속 상태와 그 시점의 불변 revision이다.

모든 적용 기록은 최소한 `assignmentId, roleVersion, agentId, workId, sessionId/runId, stateId, loadedRevision`을 기록한다. “같은 역할명”이나 같은 파일 경로는 승계 증거가 아니다. 승계는 새 실행이 허용된 `stateId`를 해석하고, 지정된 revision을 로드하고, 관련 교훈의 ID를 입력 컨텍스트에 포함하고, 그 결과가 판단 또는 행동에 영향을 준 경우에만 통과한다.

역할 변경은 새 `assignmentId`를 만든다. 책임이 추가되면 roleVersion을 증가시키고 기존 교훈의 적용 조건을 재평가한다. 겸임은 각 role의 scope를 분리해 읽으며, 해제된 assignment는 이후 새 실행에서 읽기 권한을 잃는다. 동일 역할의 새 agent는 명시된 승계 정책이 있을 때만 동일 role scope의 승인된 교훈을 읽는다. 세션·프로세스 재시작은 `stateId + revision`을 재연결해야 하며, state가 없거나 revision이 폐기·불일치이면 승계 실패로 기록하고 빈 상태 또는 명시된 안전 fallback으로 실행한다.

대안 A는 `roleId` 중심의 영속 상태다. 동일 역할의 여러 agent가 같은 역할 저장소를 읽고, agent별 실행 이력만 별도 보존한다. 구현이 작고 동일 역할 전이에 유리하다. 대안 B는 `agentId` 중심 상태에 역할별 export/import를 둔다. 귀속과 격리가 강하지만 역할 교체·공유 구현 비용이 커진다. 최소 실험에는 A를 채택하되, 저장소 자체를 role 전용으로 고정하지 않고 `stateScope`를 명시하는 방식이 적절하다. #16에서 두 구조를 모두 구현할 필요는 없으며, A의 scope·권한·revision 계약이 B로 확장 가능한지만 확인한다.

가장 강한 반례는 같은 이름의 `reviewer` 역할에 서로 다른 책임과 오래된 state를 연결해, 새 실행이 존재하지 않는 교훈을 사용하면서도 “승계 성공”으로 기록하는 경우다. 수용 조건은 loaded revision, 교훈 ID, 적용 결과가 모두 남고, 역할 버전·scope가 일치하는 것이다.

### #14 교훈 수명주기 계약

원문 사건을 정제 교훈으로 바로 승격하지 않는다. 최소 자료 구조는 다음 상태와 필드를 갖는다.

`observation → candidate → validating → accepted / deferred / rejected → superseded 또는 revoked`

각 항목에는 `lessonId`, source event/log reference, 관측 사실, 원인 가설, 적용 조건, 반증 조건, 근거 유형(D/C/A/M), 생성 revision, 검증 결과, 적용 scope, 상태 변경자와 시각을 둔다. 관측 사실과 원인 가설은 별도 필드이며, “칭찬받음”, “실패함”은 사건 증거일 뿐 원인이나 규칙이 아니다.

기술 판단은 합의된 목적·제약·검증 방법이 있고 결과가 재현 가능하면 에이전트가 후보를 검증하고 승격할 수 있다. 새로운 사용자 취향, 위험 허용 수준, 권한 부여, 제품 가치 선택은 인간 판단이 필요하다. 모든 교훈에 인간 승인을 요구하지 않되, 가치 선택을 기술 검증으로 위장하지 않는다.

후보는 적용 조건과 반증 조건이 명시되고, 독립된 재실행 또는 기존 시험으로 지지될 때 accepted가 된다. 단일 성공, 단일 불만, 원인 미확정 실패, 범위가 불명확한 일반화는 deferred다. 기존 교훈과 충돌하면 자동 덮어쓰기하지 않고 둘 다 유지하며 우선순위와 적용 범위를 판정한다. 새 근거가 기존 조건을 깨면 superseded/revoked로 바꾸고, 이후 검색은 상태와 revision을 필터링해야 한다. 철회는 저장소 표시만으로 끝나지 않고 검색 결과·캐시·입력 포함 단계에서 제외되었음을 기록해야 한다.

대안 A는 항목별 상태 머신과 append-only 이벤트 이력이다. 변경 추적과 되돌리기가 쉽고 최소 구현에 적합하다. 대안 B는 교훈을 절차 문서/스킬 버전으로 묶고 매 버전마다 전체 검증을 요구한다. 일관성은 높지만 작은 교훈 수정에도 비용이 크다. A를 기본으로 채택하고, 절차형 교훈만 B의 버전 검증을 선택적으로 적용한다.

가장 강한 반례는 한 작업에서 우연히 성공한 프롬프트를 “항상 이 방법이 정답”으로 저장하거나, 사용자의 불만을 잘못된 원인 규칙으로 확정하는 경우다. #16은 후보 생성과 승격을 분리하고, 반증 작업에서 성능이 유지되지 않으면 accepted를 취소해야 한다.

### #15 귀속·공유 계약

모든 교훈은 `ownerScope`와 `readScope/writeScope`를 가진다. 최소 범위는 `agent-private`, `role-private`, `project-shared`, `explicit-share`다. 기본값은 가장 좁은 범위인 agent-private로 시작하되, 동일 역할 승계가 목적이면 명시적으로 role-private를 지정한다. 공유는 자동 확산이 아니라 목적·대상 role/project·유효 기간·허용 revision을 포함한 share grant로 표현한다.

읽기 권한은 `roleVersion`, project, assignment 상태와 함께 확인한다. 쓰기는 현재 작업의 책임 범위 안에서만 가능하며, 다른 role의 전용 교훈을 수정할 수 없다. 지정 공유는 source lesson의 원 소유권을 변경하지 않고 별도 공유 revision을 만든다. 공유 범위를 줄이거나 assignment를 해제하면 새 실행은 즉시 해당 grant를 거부한다. 이미 입력된 과거 run은 소급 변조하지 않고, 이후 적용에서 제외한다.

충돌 우선순위는 `revoked/expired` 차단, 명시적 project 제약, 현재 role-private, explicit-share, project-shared 순으로 한다. 동일 우선순위에서 충돌하면 자동 결합하지 않고 blocked/conflict로 기록한다. 같은 내용이라도 서로 다른 role의 적용 조건이 다르면 하나의 전역 교훈으로 병합하지 않는다.

대안 A는 전면 비공유 후 명시적 share grant만 허용한다. 오염 방지가 강하지만 유용한 전이를 누락시킬 수 있다. 대안 B는 project-shared를 기본으로 하고 전용 항목만 차단한다. 편리하지만 맥락 오적용 위험이 크다. #16의 작은 실험에서는 A를 채택하고, 반복 검증된 안전한 기술 규칙만 B 후보로 비교한다.

가장 강한 반례는 role-private 교훈이 project-shared 검색에 섞여 다른 역할의 판단을 오염시키거나, 공유 후 철회했는데 캐시가 계속 해당 교훈을 주입하는 경우다. 수용 조건은 전용 비노출, 지정 대상만 노출, context 변경 시 차단, 철회 revision 이후 검색·입력에서 제외다.

### 최소 실행 경로와 후속 범위

첫 구현은 JSON 계약과 git revision을 활용한다.

1. `role/agent/assignment/session/run/state` 식별자와 scope를 기록하는 manifest를 만든다.
2. 교훈 항목과 상태 전이, 근거·조건·반증 필드를 만든다.
3. 검색기는 현재 role/project와 유효 revision을 기준으로 후보를 반환한다.
4. 적용 로그에 loaded revision, lesson ID, 입력 포함 여부, 결과를 기록한다.
5. revoke/share 변경 뒤 새 run에서 검색 결과를 다시 확인한다.

후속 이슈는 정체성·state adapter, lesson lifecycle adapter, scope/ACL과 conflict resolver, 적용 증거 수집, #16 실험 harness로 분리한다. 구현 전 각 후속 작업은 해당 이슈에 등록하고 #13~#15와 #16을 의존성으로 연결한다.

### #16 성공·실패 기준

실행 전에 역할 R/S, 경험 작업, 별도 전이 작업, 새 세션·새 실행, 예산, 반복 횟수, 성공·중단 조건을 고정한다. 같은 모델과 도구 예산으로 `no-memory`, `raw-log search`, `refined-lesson search`를 비교한다.

성공은 다음 증거가 모두 있을 때다. 경험에서 후보가 생성되었고, 검증·저장·검색·입력 포함·실제 적용이 각각 추적된다. 새 세션이 정확한 state revision을 연결한다. R의 전용 교훈이 S에 노출되지 않고 지정 공유만 전달된다. 철회된 교훈이 이후 run에 들어가지 않는다. 전이 작업에서 오류·재설명 또는 성공률이 사전 기준에 따라 개선되고, 총 토큰·호출·시간을 측정한다.

실패는 파일 저장·검색 성공만 있고 실제 판단 변화가 없거나, 같은 역할명만으로 승계를 통과시키거나, 전용 교훈 누출·철회 후 재사용·맥락 변경 오적용이 발생하거나, 개선을 주장하면서 생성·검토·검색·조정 비용을 측정하지 못한 경우다. 이 경우 해당 교훈과 계약은 효과 없음 또는 범위 초과로 기록하고, 자동 승격하지 않는다.
