# 자동 판정과 실제 내용의 분리 검토

[문서 목차](README.md) · 해당 실험 당시의 기록. 후속 결과는 목차의 연구 기록에서 확인한다.

[주 비교 문서](effectiveness-verification-20261018.md) · [원판정 코드](../scripts/effectiveness/evaluate.py)

## 실행 중 발견한 측정 한계

r003의 고정 판정은 `memory-benefit.status`가 `unproven` 대신 `experimental`이어서 실패했다. 그러나 실제 notes.md와 remaining은 경험의 인과 효과가 확인되지 않았고 전체 비용·사람 시간 절감도 미측정이라고 명시한다. 이는 ‘기억 효과가 입증됐다’는 실질적 오판으로 볼 수 없다.

공통 요청은 허용 enum을 제시했지만 `experimental`과 `unproven`의 상호 배타적인 정의를 제시하지 않았다. 따라서 이 enum 하나로 생긴 차이를 기억의 효과로 해석하지 않는다. **원판정과 점수는 수정하지 않는다.** 최종 보고에서 strict 계약 점수와 이 별도 내용 검토를 함께 보고한다. 추가 의미 검토는 결과를 본 뒤 수행하는 사후 분석이므로 새로운 사전 등록 시험이라고 부르지 않는다.

내용 검토는 현재 구현/목표의 구분, 인과 효과/시간 절감의 과장 여부, 기술 판단과 새 권한 결정의 경계, 실제 수행/제안의 구분, 사용 가능한 명령과 다음 검증의 구체성을 확인한다. 원문과 ID를 연결하며 작은 표본에서 정량적 우월성을 주장하지 않는다.

검토자는 실험을 설계한 조정 에이전트이며 독립적인 사람 또는 별도 모델의 blind review가 아니다. 원판정과 다른 판단은 이유를 명시한다. 코드의 별도 수용 리뷰도 숨겨진 판정의 완전성을 의미하지 않는다.

## 확인한 원문

- [r003 notes](../experiments/effectiveness-20261018/runs/r003/notes.md): 인과 효과 미확립, model/token 비용·인간 검토 시간 미측정, 구현과 제안의 구분, 새 공유 권한의 인간 결정을 모두 명시. 문서 내용상 효과 과장은 발견하지 못함. strict enum 실패는 그대로 유지.

- [r009 notes](../experiments/effectiveness-20261018/runs/r009/notes.md): expert-routing을 JSON에서 `unproven`으로 표기하지만 본문은 검토 중 제안이며 구현/라우팅 이득의 근거가 없다고 명시한다. 고정 판정은 `planned`만 허용하므로 이 역시 상태 라벨 차이와 실질적 구현 과장을 구분한다.
- r004, r005, r006, r008, r010, r011: 현재 구현, 계획된 runtime/routing, 기억 인과 효과 미입증, 인간 시간 미측정, 기술 검증·철회와 외부 공유 권한을 모두 구분했다. 실제로 실행하지 않은 repository 검사를 실행했다고 주장하지 않았고 제공된 명령을 안내했다. 검토 범위에서 실질적 과장은 발견하지 못했다.

이 문서들의 명령 안내는 제공된 과거 README/pilot을 기준으로 한다. 별도 Windows 재검증에서 드러난 기존 자료의 UTF-8/줄바꿈 문제는 worker에게 제공되지 않은 새 관측이므로 그 설명을 worker의 기억 실패로 채점하지 않는다. 실제 고객용 최종 문서로 채택할 때에는 이 제한을 반영해야 한다.

전체 원판정 결과는 [주 비교 보고서](effectiveness-verification-20261018.md)에 있다.

## 코드의 실제 실패와 채택 범위

[r012 tracker.py](../experiments/effectiveness-20261018/runs/r012/tracker.py)는 `i.get('status','open')`으로 누락된 status를 검증 중에만 open으로 간주하고, 저장 상태에는 status를 채우지 않는다. 숨겨진 `missing_status` 판정을 실패했다. 이는 문서 enum 표현 차이와 다른, 실제 import 상태 검증 누락이다. 원래 시험과 자신이 작성한 시험이 통과해도 별도 판정에서 놓친 경우를 보존한다.

r014의 두 번째 무기억 코드 실행도 같은 `missing_status` 판정을 실패했다. 기존 `scripts/work_pilot/evaluator.py`의 상태 검사도 이미 `status in {open, done}`을 요구한다. 따라서 누락 상태를 그대로 저장하는 것은 이번 숨겨진 판정에만 맞추지 못한 표현 문제가 아니라 기존 소비자가 거부할 상태를 만든 것이다.

또한 r012는 DESCRIPTION의 기존 예시/설명을 축약했다. 원 회귀가 모든 public describe 내용을 고정하지 않으므로 시험 통과를 완전한 호환성으로 해석하면 안 된다. 실제 소유 모듈에는 r001에서 검토한 import 경계만 최소 변경으로 반영했으며, 다른 후보를 자동 채택하지 않았다. r001 역시 그대로 복사하지 않고 상대 경로·깊은 계층 반례를 보완했다. 사전 코드 점수는 고정 판정의 통과이며 배포 가능성에 대한 완전한 증명은 아니다.

r013 인계 문서도 현재 구현/계획, 도구 시험/효과, 기존 기술 권한/새 외부 공유 권한을 구분했고, 제안된 검사와 실제 실행을 혼동하지 않았다.

r019 원문 로그 조건의 문서 역시 구현/효과를 과장하지 않았다. expert-routing을 `unproven`으로 쓴 strict 실패는 r009와 같은 enum 의미의 모호성이다.

r021도 도구 구현과 계획된 runtime/routing, 기억 인과 효과·사람 시간 미측정, 기존 기술 권한과 새로운 공유 권한을 구분했다. 따라서 11개 인계 문서 모두에서 이 검토 범위의 실질적 과장은 발견하지 못했다. 이는 원판정 실패 3개를 지우거나 별도의 독립 정량 평가를 통과했다고 선언하는 것이 아니다.

r018 교훈 제외 조건은 코드 검사에는 통과했지만 작업 완료에 실패했다. 최초 child 완료 때 사용한 올바른 test_candidate.py hash를 root 완료 요청에서 잘못 옮겨 적었다(`...fe8f3f48...`가 `...fe8e3f48...`로 바뀜). 도구의 hash mismatch를 workspace 해석 문제로 잘못 설명하고 child를 reopen한 다음 같은 오타를 재사용해 실패했다. 최종 답변은 미완료를 인정했지만 child/root 모두 열린 채 끝났다. 이는 증거 문자열 전사와 실패 복구의 실제 행동 실패이며, 코드 검사 성공과 별도로 보존한다.

A(제외)와 R(실제 adapter 철회)는 각 업무에서 **worker에게 제공한 task와 memory의 byte hash가 각각 동일**하다. 내부 저장 이력·revision과 receipt는 다르지만 모델이 받은 내용은 같다. 코드 A는 hash 전사에서 실패하고 R은 완료했으므로, 이 한 쌍을 특정 교훈의 필요성/철회 후 행동 변화에 대한 안정적인 증거로 해석할 수 없다. adapter의 새 조회에서 철회 교훈이 빠진 사실과 모델 행동의 원인은 별개다.
